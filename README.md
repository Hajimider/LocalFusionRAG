# LocalFusionRAG

## 一、引言

### 1、项目背景介绍

法律资料通常分散在法条、历史版本和判例文件中，文件格式也不统一。用户用自然语言提问时，单纯依赖关键词搜索容易漏掉语义相近的内容；直接让大模型回答又可能混用法律版本、把个案结论当成一般规则，或者在资料不足时自行补充。

LocalFusionRAG 是一个面向中文法律资料的本地混合检索与辅助分析系统。项目把已下载或获授权的法律资料统一导入知识库，经过文档解析、切分、向量化、关键词检索、重排序和引用校验后，再交给本地模型或兼容 API 生成回答。

### 2、目标与意义

本项目的目标是把法律资料检索和大模型问答连接起来，让用户可以在本地完成资料导入、索引构建、证据检索和辅助分析。项目重点解决以下问题：

- **降低资料查找成本**：将分散的 PDF、DOCX、Markdown 和 TXT 文档统一处理，支持按文档类型和效力状态筛选。
- **减少单一路径漏召回**：同时使用 BGE 语义检索和 BM25 关键词检索，兼顾自然语言表达与法条编号、案号等精确词。
- **保留回答依据**：为召回片段编号并展示文件、页码、文档类型和命中内容，方便回到原文核对。
- **控制无依据回答**：通过重排序分数和校准阈值判断证据是否充分，资料不足时先拒答，不强行生成法律结论。
- **支持本地部署**：检索模型、索引和可选 GGUF 大模型均可放在本地，API 只作为可切换的回答后端。

### 3、主要功能

- 支持 PDF、DOCX、Markdown 和 TXT 文档导入，并保留来源、标题、类别、效力状态等元数据。
- 支持 DOCX 段落和表格提取，PDF 按页读取，Markdown 可使用 YAML front matter 补充法律字段。
- 使用 BGE、FAISS、BM25、RRF 和 CrossEncoder 完成混合召回与重排序，模型不可用时自动回退。
- 支持现行法条、历史法条、判例检索、案件分析、法律对比和时间线等意图路由。
- 支持查询改写、法律资料筛选、低置信度拒答、来源引用和 NDJSON 流式输出。
- 支持本地 llama.cpp/GGUF 和 OpenAI 兼容 API 两种回答后端，均通过 FastAPI 网页使用。
- 支持标准库爬虫采集白名单内的公开法律页面，并记录 robots、限速、去重和失败状态。

## 二、技术实现

### 1、环境依赖

#### 1.1 技术资源要求

- **Python**：建议使用 Python 3.10 或更高版本。
- **操作系统**：Windows、macOS、Linux 均可，项目接口使用 FastAPI 和标准 Python 命令。
- **内存**：索引规模越大，文档切分和 BGE 向量化占用的内存越高；3,183 份 DOCX 的首次建库需要预留足够内存和磁盘空间。
- **模型文件**：Embedding 和 Reranker 可以填写本地目录；回答模型可以使用外部 GGUF 文件，也可以改用 OpenAI 兼容 API。
- **GPU**：项目不依赖 GPU，BGE、FAISS 和 llama.cpp 可以在 CPU 环境运行，但首次建库和本地大模型生成会更慢。

#### 1.2 项目设置

进入项目目录后安装依赖：

```shell
python -m venv .venv
python -m pip install -r requirements.txt
python -m pip install python-docx
```

`python-docx` 用于读取 DOCX 段落和表格。只有本地 GGUF 模式需要额外安装 `llama-cpp-python`；CPU 环境可按当前平台选择对应的预编译包，API 模式不需要安装该依赖。

完整 CrossEncoder 需要 `sentencepiece` 和 `protobuf`，两项依赖已经写入 `requirements.txt`。如果暂时没有 Reranker 权重，可以把 `RERANKER_MODEL` 留空，系统会使用轻量重排序回退。

#### 1.3 项目运行

项目提供 IDE 一键启动入口。打开 `start_web.py`，只修改文件顶部的主要配置，然后直接运行：

```shell
python start_web.py
```

服务启动后访问 `http://127.0.0.1:8000`。首次使用需要先准备法律资料并点击“构建索引”；已有索引时可以直接进入问答。

#### 2.1 当前的项目版本及未来规划

- **当前版本**：法律领域本地混合 RAG 版本。
  - [√] 支持 PDF、DOCX、Markdown、TXT 文档解析。
  - [√] 支持 BGE、FAISS、BM25、RRF 和 CrossEncoder 检索链路。
  - [√] 支持现行法条、历史法条、判例检索和案件分析意图路由。
  - [√] 支持本地 GGUF、OpenAI 兼容 API、引用校验和低置信度拒答。
  - [√] 支持索引版本化、SHA-256 校验、原子切换和跨进程锁。
  - [√] 支持 FastAPI 网页、文档上传、流式问答和健康检查。
  - [√] 支持公开资料白名单爬虫，遵守 robots 和站点限速规则。

- **未来规划**：
  - [ ] 增加更多经过授权的法律问答和判例评测数据。
  - [ ] 使用人工标注数据进一步校准证据充分性和拒答边界。
  - [ ] 增加法律版本冲突检测和增量索引，减少重复处理。
  - [ ] 在有合适训练数据和算力时，尝试法律领域 Reranker 微调。

#### 2.2 核心 Idea

项目采用“索引、检索、生成”三阶段 RAG 流程。先把法律资料解析为带元数据的文本块，再分别建立 BGE 向量索引和 BM25 关键词索引；用户提问后进行意图判断和查询改写，使用双路召回、RRF 融合和 CrossEncoder 重排序定位候选证据；最后由本地 GGUF 模型或兼容 API 基于证据生成带引用的回答，证据不足时直接拒答。

#### 2.3 使用的技术栈

本项目使用 LangChain 文档对象和文本切分器完成资料处理，使用 BGE 完成 Embedding，FAISS 保存向量索引，BM25 和 RRF 完成混合检索，CrossEncoder 完成候选重排序，FastAPI 提供网页和流式接口，llama.cpp 负责本地 GGUF 推理。

| 层次 | 技术 | 作用 |
| --- | --- | --- |
| 文档层 | LangChain、PyPDF、python-docx | 读取 PDF、DOCX、Markdown 和 TXT |
| 表示层 | BGE Embedding | 把问题和文本块编码为语义向量 |
| 检索层 | FAISS、BM25、RRF | 完成向量召回、关键词召回和排名融合 |
| 排序层 | CrossEncoder | 对候选问题和文本块联合打分 |
| 编排层 | 查询改写、意图路由、Prompt | 为不同法律任务选择检索条件和生成模板 |
| 生成层 | llama.cpp、GGUF、OpenAI 兼容 API | 根据检索证据生成回答 |
| 服务层 | FastAPI、Uvicorn、原生网页 | 提供上传、建库、问答和健康检查 |

## 三、应用详解

### 1、核心架构

系统可以分为文档层、索引层、检索层、生成层和服务层：

```text
法律资料（PDF/DOCX/Markdown/TXT）
        ↓
LangChain 加载、元数据解析、重叠窗口切分
        ↓
BGE 向量化 ───────────────→ FAISS 版本化索引
        ↓
中文 BM25 关键词索引
        ↓
查询改写与法律意图路由
        ↓
BGE 语义召回 + BM25 关键词召回
        ↓
RRF 融合 → CrossEncoder 重排序 → 证据充分性判断
        ↓                         ↓
本地 GGUF/API 生成 ← 低置信度拒答
        ↓
FastAPI 页面返回回答、来源和流式状态
```

### 2、索引-indexing

本节说明法律知识库的加载、读取、文本切分、向量化和 FAISS 索引过程。索引构建不会直接覆盖当前版本，而是先写入新版本目录，校验完成后再切换活动指针。

#### 2.1 知识库搭建-加载和读取

法律资料放置在 `knowledge_base/legal_docs/`，也可以在 `start_web.py` 中把 `KNOWLEDGE_DIR` 改成项目外部目录。推荐使用官方或获授权资料，例如：

- [国家法律法规数据库](https://flk.npc.gov.cn/)
- [人民法院案例库](https://rmfyalk.court.gov.cn/)
- [中国法院网](https://www.chinacourt.org/)
- [中国裁判文书网](https://wenshu.court.gov.cn/)

系统支持以下文件：

- **DOCX**：读取段落和表格，按所在目录生成待核验的法律类别。
- **PDF**：按页读取并保留页码，旁车 JSON 可以补充法律元数据。
- **Markdown**：支持 YAML front matter，填写 `doc_type`、`validity`、`jurisdiction`、日期、法院、案号和来源链接。
- **TXT**：按文本文件读取并保留来源路径。

当前法律语料包含 3,183 份可读取 DOCX，提取约 1,664 万字符，切分后约为 40,781 个文本块。DOCX 的效力状态需要人工核验；系统不会根据文件名自动把未知资料认定为现行有效法律。

项目也提供标准库爬虫。先在 `data/legal_seed_urls.txt` 中填写公开页面 URL，再运行 `start_legal_crawler.py`。爬虫只访问白名单域名，遵守 `robots.txt` 和站点限速，不登录、不处理验证码、不绕过访问控制；HTML 会转换为带 front matter 的 Markdown，PDF 会生成旁车元数据文件，并通过正文哈希跨运行去重。

法律资料的版权、访问许可和个人信息处理由资料提供者负责。未获授权的批量案例和真实 API Key 不应提交到 GitHub。

#### 2.2 文本分割和向量化

长文档不能整体放入上下文，因此使用 LangChain 的 `RecursiveCharacterTextSplitter` 按中文段落、句号和逗号等边界进行重叠切分。默认网页建库使用 `chunk_size=500`、`chunk_overlap=80`；公开检索实验使用 `chunk_size=300`、`chunk_overlap=50`。

重叠窗口可以减少法条被切在边界两侧时的语义损失，但重叠过大会增加向量数量和重复召回。每个文本块都会保留来源、页码、标题、类别、效力状态和块编号，便于后续展示和核对。

#### **2.3** 向量数据库

项目使用 BGE 把问题和文本块编码为向量，再用 FAISS 完成 Top-K 近邻搜索。FAISS 索引和元数据按版本保存，构建过程包含以下步骤：

1. 文档解析、切分和向量计算完成后，先写入临时目录。
2. 生成 `index.faiss`、`index.pkl` 和索引清单，并计算 SHA-256 校验值。
3. 在进程锁和文件锁保护下创建新版本目录。
4. 原子更新 `CURRENT` 指针，查询只读取完整版本。
5. 保留最近两个可用版本，构建失败时不破坏旧索引。

这种设计避免了重建索引时页面读到半成品文件，也方便在新版本异常时恢复到上一版本。

### 3、检索-Retriever 和生成-Generator

#### 3.1 向量数据库检索

用户问题先经过规则或模型意图路由。法律意图包括现行法条、历史法条、判例检索、案件分析、法律对比和时间线；其中现行法条和历史法条会自动设置效力筛选，判例检索和案件分析会优先检索判例资料。

检索阶段同时运行两条路径：

- **BGE/FAISS 语义检索**：适合表达方式不同但含义接近的问题。
- **BM25 关键词检索**：适合法条名称、条款编号、案号和法院名称等精确词。

两路结果使用 RRF 按排名融合，避免直接相加不同量纲的分数；随后使用 CrossEncoder 对少量候选片段重新排序。CrossEncoder 权重或推理不可用时，系统回退到 BGE 向量重排序，再失败时保留 RRF 顺序，并在状态中返回实际使用的后端。

项目在固定公开的 `C-MTEB/T2Reranking` 子集上进行检索消融，包含 99 个查询和 1,591 篇候选文档。Hybrid + Reranker 的结果为：`Hit@5=0.9798`、`Recall@5=0.4193`、`MRR=0.7983`、`NDCG@5=0.6374`。这是一组固定公开子集上的实验结果，不是 C-MTEB 官方全量排行榜成绩。

#### 3.2 大模型 llm 的调用

项目把检索链路和回答模型解耦，支持两种后端：

| 后端 | 调用方式 | 适用场景 |
| --- | --- | --- |
| 本地模型 | `llama-cpp-python` 加载 GGUF 文件 | 资料不离开本机，适合离线演示 |
| API 模型 | OpenAI 兼容 Chat Completions 接口 | 不需要本地加载大模型，可按服务商切换 |

两种后端共用同一套检索上下文、Prompt、引用格式和流式输出协议。项目目前没有使用 vLLM，也没有微调回答模型；本地推理主要面向 CPU 友好的 GGUF 模型。

#### 3.3 prompt 和构建问答链

问答 Prompt 会明确告诉模型：只能根据检索证据回答，资料不足时说明无法确认，并保留 `[资料N]` 引用。系统会在生成前校验重排序分数和证据数量；低于校准阈值时返回拒答，不把空上下文交给模型。

流式接口 `POST /api/chat/stream` 使用 NDJSON 依次返回检索来源、回答片段和完成状态。页面可以展开查看来源文件、PDF 页码、文档类型、效力状态、命中片段和重排分数。

本地拒答流程使用 18 题校准集选择阈值，再在独立 18 题测试集上固定评估，避免用测试题反复调参。独立测试准确率为 0.9444，拒答召回率为 1.0000。该结果属于当前示例知识库的开发验证，不代表法律领域的生产效果。

# 3.总结与展望

## 3.1 本地法律知识库关键点总结

1. **数据处理**：使用 LangChain、PyPDF 和 python-docx 解析多格式法律资料，保留文件、页码和法律元数据，并把 3,183 份 DOCX 切分为约 40,781 个文本块。
2. **混合检索**：使用 BGE/FAISS 处理语义召回，使用 BM25 处理精确词，再通过 RRF 融合并用 CrossEncoder 重排序。
3. **可信生成**：通过查询改写、意图路由、引用编号和拒答阈值限制回答范围，模型调用失败时返回可解释的降级信息。
4. **工程可靠性**：使用 SHA-256、版本化目录、原子切换和跨进程锁保护索引，FastAPI 页面支持上传、建库、流式问答和健康检查。
5. **评测方法**：使用公开检索子集比较 Dense、BM25、Hybrid 和 Hybrid + Reranker，并把拒答阈值校准集与独立测试集分开。

公开检索结果仅用于验证检索和重排序链路，法律资料的效力状态、适用范围和案件结论仍需回到权威来源人工核对，系统不能替代律师判断或正式法律意见。

## 3.2 未来发展方向

1. **数据集扩充**：增加经过授权的法律问答、法条版本和判例相关性标注，按法条、判例和跨文档问题分层评测。
2. **检索优化**：在现有固定阈值基础上，尝试使用少量可解释的 ML 证据充分性分类器，并比较拒答误报和漏答变化。
3. **模型优化**：在有合适硬件和标注数据时，微调法律领域 Reranker
4. **工程完善**：增加增量索引、法律版本冲突检测、权限控制和更细粒度的引用校验。
